# 企业制度知识助手与报销材料预审系统：方案 v0.1

日期：2026-10-20方案，2026-10-23状态更新。Chatflow第5版、预审Workflow第4版；材料/模型/规则闭环已接本机网页与独立复核记录（WEB-001）。第5版交通批准查询优先与限定真实证据回退见CHATFLOW-005。本机开放角色演示不代表正式认证或真实人工审核；正式权限、更正审计及完整交付仍为设计目标。

## 1. 目标、用户和边界

目标岗位为初级 AI Agent / AI 应用开发。项目证明完整 RAG、Dify 业务编排、Python/API 集成、评测调优和可复现交付。既有售后项目用于证明受控执行和可靠性；本项目不重复其复杂审批执行系统。

用户为员工与财务复核人员。员工咨询制度和提交材料；财务查看预审依据、标记复核结果。第一版单个合成企业，差旅住宿、交通、餐费三类。不做多租户、不接真实企业系统、不付款、不作发票验真、不承诺税务合规。上传内容为待分析材料，不能成为系统指令或改变鉴权。

成功标准：制度回答可追溯、信息不足时追问、无依据时不编造；申请金额与材料问题可代码核对；预审、复核和失败状态真实；新环境可重建并复跑固定评测。

## 2. 架构与职责

| 子系统 | 设计职责 |
|---|---|
| Dify 知识库 | 制度文档解析结果、切片、embedding、检索和重排配置 |
| 制度助手 Chatflow | 意图/缺项识别、多轮补充、按适用版本检索、回答与引用 |
| 预审 Workflow | 收集申请、处理材料、调用校验、检索依据、生成结构化结果 |
| Python FastAPI | 可信用户上下文、输入校验、Decimal 金额计算、版本规则、持久化、Dify API 适配 |
| SQLite | 单机演示的用户、申请、结果、复核及运行记录；无需重复部署第二套业务数据库 |
| 简单应用网页 | 制度咨询、申请提交、结果/引用查看、人工复核；UI 在链路稳定后开发 |

业务浏览器请求先进入 Python 后端，再调用 Dify 应用 API；百炼 Key 配在 Dify，Dify 应用 Key 存后端；不下发浏览器。Dify 工作流需回调 Python 规则接口，因此两者网络必须双向可达。业务权限由后端核验，不能依赖前端传来的 user_id 或 Dify user 参数完成授权。

运行路线默认优先评估本地 Dify + 本地 Python；Docker 内 localhost 指容器自身，接口使用选定容器服务名或明确主机地址。Cloud + 云端 API 是资源不足时的替代。临时 SSH 隧道只作联通证据，不作为默认交付路线。

## 3. 业务数据与知识入库

独立编写合成差旅制度、材料要求、费用标准表及两个生效版本，包含冲突/失效/缺失样本。范围只涉及上述三类费用。语料数量按覆盖需求确定，不为凑文档数量制造重复数据。

每份制度有 policy_id、version、生效区间、原始来源、文件哈希；每个片段有 clause_id、段落/页定位。制度正文与结构化金额规则由同一版本清单关联，入库时检查一致性。PDF 不存在可靠页码时使用实际段落定位，不能虚构页码。

第一版支持 Markdown、可提取文本 PDF、UTF-8 CSV 费用明细；图像、扫描 PDF、Excel 和复杂票据解析后置。解析为空/乱码/表格丢失时停止自动判定并提示人工处理。不得把 OCR 未实现写成已支持发票识别。

入库记录解析结果、分段配置、embedding 模型及导入状态；支持按来源哈希跳过重复导入和替换指定制度版本。DSL 不包含知识库内容，另提供语料与重建说明/脚本。

先建立按标题/条款分段的向量检索基线；再分别比较切片大小、混合检索、rerank。适用版本/员工范围先过滤，检索后仍校验出处范围，不能让模型随意选择政策版本。Dify 原生能力不足时以最小外部接口补齐，不先另建完整 RAG 平台。

## 4. 两条应用流程与接口边界

### 制度咨询

输入问题及可信员工上下文；识别是否缺日期/费用类型等必要条件 → 多轮追问 → 解析适用制度版本 → 检索 → 检查引用与依据 → 回答或说明无法判断。会话变量用于本次对话状态，不宣称为跨会话长期记忆。

固定业务路由以 Chatflow 为主；仅当任务确需自主选择工具时增加有界 Agent 节点。是否加入 Agent 扩展由可演示的业务增益决定，不为简历标签强行加入。

### 材料预审

员工提交申请与费用明细 → 校验/解析 → 模型提取非结构化信息 → 服务端验证提取结果 → 代码检查合计、期限、标准、重复与缺项 → 检索对应条款 → 汇总逐项问题 → 保存报告。模型不能覆盖代码计算结果；金额不确定时需人工复核。

预审结果分为未发现问题、需补材料、需人工复核，保留逐项 findings、依据、规则/制度版本及真实运行 ID。它不是批准付款。财务复核另存操作者、时间、处理结论和备注，不覆写原预审；仅本人申请和有权限的财务角色可查看。

API 能力最小集：申请创建/查询、预审发起/结果、人工复核、制度版本查询、内部规则校验；外层以 Python 的 OpenAPI 为契约，内部 Dify 输入/输出由 Pydantic 校验。异步预审返回 job_id，以实际 pending/running/completed/failed 状态查询；重试沿用作业标识避免重复业务记录。

报告以结构化 JSON 为事实来源，Markdown 为展示。首版允许下载 JSON 与打印网页，Word/PDF 专用生成后置，避免报告排版抢占 RAG 任务。

异常覆盖模型/检索/HTTP 超时、401、429、格式不合法、解析失败、无适用制度。失败显式呈现；有限重试，不把失败回退为 mock 成功，不对不确定金额给出自动通过结论。

## 5. 评测与验收

计划 100 条人工核对制度问答（60 调试、40 保留）与 40 份合成申请（24 调试、16 保留）。按制度/场景分组拆分，避免仅换措辞泄漏；保留集开发期间不用于提示词调参。规模与结果一起报告，不能把样本分数当真实生产准确率。

问答覆盖单条款、多条款、追问、跨版本、无答案、冲突和干扰指令。记录条款 Recall@K、引用有效性、人工答案正确性和无依据拒答情况。申请按逐项问题检查金额、缺项和异常转人工，计算问题识别 precision/recall 与报告正确性；确定性运算用代码断言，模型裁判仅辅助。

固定数据/模型/温度/版本，先输出基线报告，再一次只改一个检索因素；记录样本级结果与 badcase。模型评测和无模型工程回归分开。耗时、输入/输出 token、模型费用与券抵扣分开记录；没有货币账单不能声称金额已核实。

功能验收要求金额和权限测试全部通过；无法解析、缺失依据、越权和上游失败均能按设计处理。效果报告如实展示未达标案例，不预设虚构 95% 指标。报告保留数据、代码、DSL、插件和模型版本，可重跑同一测试。

## 6. 实施顺序与交付

1. 环境：核查资源/原服务，锁定 Dify 版本与插件，确定稳定双向网络，测试重启后互通。
2. 数据：编写合成制度与规则、入库/定位清单、问答标注和保留集。
3. RAG：完成最小 Chatflow、来源查看、追问和拒答；保存真实基线。
4. 预审：规则 API、Workflow、数据库和真实结果；先单申请闭环，再有限批量处理。
5. 集成：简单网页、权限、作业状态和人工复核；接通用户场景。
6. 优化：对照实验、失败修复、回归与成本/延迟统计。
7. 交付：独立 GitHub 仓库、脱敏 DSL、锁定依赖、数据重建、部署复现、演示录屏和简历事实清单。公网演示可选且后置。

原有售后服务不得被覆盖；新项目容器、端口、卷和数据库均独立命名。公网部署/新资源费用/发布目标尚未确定。

GitHub 发布前检查全部文件和历史，不上传 `.local`、凭据、人员信息、真实发票、Cookie 或原始日志。原创部分拟采用 MIT，正式发布前确认；底座和插件保留各自许可。独立复现验收要实际导入 DSL、重建知识库并跑代表样例，不能只验证网页能打开。
