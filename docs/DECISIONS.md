# 设计决策

## D023：先交付白名单源码包，在独立目录验收，不分发私有运行状态

当前远程目标和原创代码许可证未定，先生成可审查的本地候选。白名单选择源码/测试/文档/合成数据，排除.local/vendor/DB/上传/日志；逐文件哈希及DSL环境值/绑定/Header检查不依赖.gitignore。交付副本人工审核置空，原用户证据不改、不迁移授权。解压到新目录运行测试与离线命令，只证明无原私有状态依赖，现有Python依赖复用不算全新安装/Docker重装。原40冻结源及历史结果不改。见DELIVERY-001；独立仓库发布仍待用户选定目标，不复用售后项目。

## D022：保留第4版冻结源，第5版分阶段修复并明确原文回退

首轮已见Q01–Q08登记为开发；40文件冻结副本与原结果不覆盖。原始节点证明5拒答均model_unsupported，Q05确缺交通/预审，不放宽结构或版本校验。提示单因素仅部分改善后，采用交通批准意图查询优先与限定必要条款的真实片段回退；餐费材料强制原文，不重复生成例外。日期单独更正只清除被替代日期。新builder与模板复现第5版，旧builder保留第4版，避免破坏首轮追溯。当前原文策略是输出约束，不是模型推理根治或语义准确率；具体证据及剩余边界见CHATFLOW-005。取代“Q05/5拒答仍未定向处理”的当前结论。

## D021：前瞻性评测先冻结与人工标签审核，避免开发回归冒充保留成绩

先建8问答+8申请助手原创候选与接触史，独立2份开发pilot仅检验工具；已有制度/工程家族重叠必须披露，不称盲测或未见家族泛化。输入/gold/代码/DSL/制度及主工具哈希冻结，相应标签未有真实人类声明则三个正式入口在联网前停止。问答条款提及不当作语义正确或召回率；材料问题按code+明细+条款多重集比较，失败保留在整体分母，未定义指标为null。首轮报告/运行标记不覆盖，调参后原候选转开发、另立版本。见EVALUATION-001；本轮只有两份开发真实试跑，没有正式保留成绩。

## D020：本机同源网页与独立复核，明确开放角色演示边界

静态HTML/CSS/JS由既有18082 FastAPI提供，不加构建链或隧道；原Bearer只在后端/私有工具保留，浏览器用随机HttpOnly/SameSite演示会话及同源写请求校验。员工/财务profile服务端固定映射，但任何本机访客可选，不能宣称正式身份核验或上线权限。财务跨员工只通过角色受限接口；复核存独立表并绑定已完成报告哈希，不覆盖规则输出，每报告只保存一次，暂不支持更正。现有制度源经快照匹配后展示引用正文，明确不是新RAG检索。见WEB-001；正式认证/审计须在公开部署前另做。

## D019：输出格式修复只改提示协议，不静默修补模型候选

提取协议升级至travel-extract-1.0.2，明确空值对象、冲突字段名数组及原始JSON输出。保留原格式失败与中间围栏失败，不自动剥围栏、转换对象或放松证据/金额/日期核验。相同材料按新协议产生新任务，真实回归区分fresh_model_task与缓存；七条开发观察不等于正式准确率。当前第4版取代D018中两处格式问题仍待修复的状态，其余证据边界保持，见EXTRACTION-002。

## D018：模型只出候选，服务端核验后才能创建申请

同一预审Workflow第2版增加原文提取分支，保留原规则调用兼容；复用已有密钥，不让业务前端直接采信Dify候选。Markdown/PDF先提取本地文本，模型给七字段及逐字引用；服务端检验结构、有限字面证据、明确日期角色/多值冲突、CSV日期和金额一致性，缺项/冲突/格式错误不建申请。保存原文、原模型输出、页码/行号、版本和运行ID，业务申请同时关联说明与CSV。当前两处真实格式偏离按人工核对处理，不以容错掩盖为正确提取；见EXTRACTION-001。SQLite v3只增加关联与提取任务表。

## D017：CSV先确定性解析，保留原始证据，禁止部分成功入申请

费用明细CSV无需模型猜字段；用严格UTF-8/列名/类型/金额/日期校验，单行错误使整文件invalid。材料原始BLOB、哈希、解析版本与行定位保存到私有SQLite，按员工隔离；申请仅从本人parsed记录组装，客户端不能替换解析结果或身份，幂等包含来源。新增schema v2前备份旧库，兼容纯JSON申请。布尔材料声明不当作凭证事实；自由文本模型提取及PDF/OCR仍后置，见MATERIALS-001。

## D016：本机业务后端绑定身份，先保存不可修改申请与单次任务

业务API运行于主机回环18082，复用现有本地Dify适配器；Dify再调用规则容器，不新增隧道/网络配置。身份用本机演示Bearer映射，不信任申请中的员工ID/类型/角色；仅DEMO-001具备当前规则范围。SQLite保存申请、任务、报告与状态事件，唯一约束及条件领取防止并发重复创建/执行；不可修改申请、每申请单任务，错误更正需新申请。未知远端结果记indeterminate且不自动重试，不声称exactly-once。首版单进程线程执行器，重启不自动恢复遗留任务；独立队列、正式认证和跨申请历史规则仍待做。真实验收见BUSINESS-001。

## D015：本地容器规则服务与Dify精确域名放行（已实际联通）

取代D004中本轮运行拓扑未决状态：规则API使用独立policy-rag-rules Compose项目，加入现有Dify网络，主机只绑定127.0.0.1:18081；Dify经SSRF代理访问policy-rules:8000。仅通过官方配置放行精确服务名，不开放整个私网或依赖临时隧道。规则请求/报告用Pydantic约束，错误非200不转成功。当前先完成无模型结构化预审；材料提取及RAG说明后续实现，不为流程增加无业务必要的生成节点。见WORKFLOW-001。

## D013：餐费处理分支展示真实依据原文（第4版，取代D012的该分支生成策略）

真实重放既出现保守拒答，也出现词形过滤未覆盖的核定表述。对已识别的餐费处理问题，要求本次同版本MEAL/REVIEW齐备，再只展示对应真实检索片段；缺证据仍拒答。每日限额问法允许完整MEAL依据上的原文回退。保留生成/原文/拒答状态，不以原文展示充当模型正确回答成绩；其它问答仍保留生成。此限定修复通过八轮真实预览及发布页验收，见CHATFLOW-004，不能推导为通用语义安全。

## D014：规则先实现纯函数，再接HTTP与Workflow

Decimal计算与制度版本、城市配置共用单一源，报告只输出问题和事实，不核定报销金额。原城市列表结构化后，两版渲染哈希与既有入库文档一致，不重新入库。跨申请票据历史必须来自可信服务端，身份和材料声明不能当作已验证事实。当前离线实现已测试，HTTP契约、网络、鉴权和持久化仍待完成，见RULES-001；不把离线模块记作API或业务系统验收。

## D001：项目定位（已确定）

面向初级社招的 RAG + 工作流应用交付。与原售后 Agent 的可靠执行能力互补，不重做工单，不以节点数和框架数量作为成果。

## D002：业务边界（方案默认）

从差旅报销的住宿、交通、餐费开始；使用合成数据。只做预审和人工复核，不付款、不验真、不自动作财务审批。其它制度领域后续按收益扩展。

## D003：规则与模型分工（已确定）

金额计算、字段校验、权限、版本选择用代码；RAG 提供出处，模型提取和解释。规则和制度以共同的版本清单关联，禁止模型临时生成报销金额规则。

## D004：运行拓扑（未决，开发前置）

Dify Cloud 到主机可联通，但当前免费 SSH 隧道多次重置并更换 URL。不能把它定为长期方案。默认先评估本地 Dify + 本地 Python API；资源不合适时采用 Cloud + 云端 API，不能未经核查直接安装或产生云资源费用。

## D005：复用策略（已确定）

不 fork 相似项目作为整套底座。参考合同审查应用的 API 集成、报销示例的分层与交互、Ragas 的评测方法。复用具体代码前固定来源和 commit；无明确许可的材料不复制发布。

## D006：评测与交付（已确定）

独立调试集与保留测试集；代码断言为确定性规则判定依据，人工标注为问答参考，模型评分只辅助。优先本地可复现与录屏，公网演示后置；所有效果数字来自实际记录。

## D007：检索基线版本隔离（已确定基线策略）

先用两个版本隔离知识库，代码按出差开始日期选择，避免依赖未实测的元数据过滤。向量检索top_k=3，无重排和阈值；知识库/embedding已真实建立，首次检索见BASELINE-001。100/40评测为后续目标，当前只有12条调试草稿，不假装达到规模。

## D008：本地分时部署（配置已确定，稳定性待测）

用户要求保留Edge并启动Docker，随后明确允许停止全部旧容器专做Dify。选择官方tag1.17.1、新Compose项目policy-rag、本机18080端口；禁用collaboration，Celery并发1。旧13个容器只停止并保存恢复清单。镜像层/WSL全局位置不迁移，不改旧项目资源配置。须健康与实际模型/检索验收后才能称环境稳定。


## D009：最小问答采用确定性日期路由与引用成员校验（已实现）

日期只接收完整年月日；缺失/无效/多日期先追问，无唯一制度转人工。代码选版本后检索隔离知识库，不让模型猜版本。会话变量只存待补日期的问题，不自动继承上一问题日期。LLM输出supported/answer/clause_ids，代码验证条款在本次检索且版本正确，结构异常拒答；不能把成员校验写成语义蕴含或幻觉已消除。真实验收及边界见CHATFLOW-001。

## D010：CITY提示策略先作为候选实验（历史阶段，现由D011取代接入状态）

保留BASELINE-001；查询增加城市等级提示，三条调试草稿有改善，但未人工审核、未在独立保留集验证，因此只加入评测工具的显式city-hint选项，暂不修改已发布Chatflow。下一步扩大回归后决定是否接入，见RETRIEVAL-EXPERIMENT-001。


## D011：CITY通过开发回归后接入，保留关联依据失败（已实现）

全9条检索对照2条改善、7条召回率不变、0条下降，18次请求无错误/跨版；在保留原版DSL后接入同一应用，真实问答回归后发布第2版。评测和DSL共用转换函数，LLM原问题不变，仅检索查询追加提示。此决策取代D010的“暂不接入”，不取代独立测试/人工审核要求。D03初核补REVIEW后暴露关联依据漏召回，作为下一因素独立处理；见RETRIEVAL-EXPERIMENT-002。


## D012：关联依据最多补检索一次，区分主Recall与上下文覆盖（已实现）

D03只命中MEAL不足以解释处理路径。保持city-hint主top3，餐费处理问题缺同版本REVIEW时再检索一次top1，只追加真实命中的目标片段，上下文最多4条；不增大主top_k或从本地源文补答案。与主结果配对比较并记录额外请求，合并覆盖不能称Recall@3。取代D011中“D03关联依据仍未处理”的当前状态，原向量检索本身仍漏REVIEW。

回答必须实际引用MEAL/REVIEW，supported只表示依据充分而非允许报销；需要解释规则和人工路径，禁止推导核定金额。已识别越界表述被代码拒绝，未证明语义安全或金额计算可靠。发布第3版时明确保留简短问法补日期后的保守拒答，不为可答率放松约束。
